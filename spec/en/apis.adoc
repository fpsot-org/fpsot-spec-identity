= Tokens at APIs
include::_fpsot-terms.adoc[]

These rules set how an {abbr-api-first} accepts and checks an {term-access-token}.
They add to the access control rules of the {abbr-api} design specification, API-090 to API-093.
Errors go in the format of the page xref:errors.adoc[Errors].

== Checking a token

[[IAM-030]]
*IAM-030.* An {abbr-api} MUST accept only tokens that the authorization server issued for that {abbr-api}.
The `aud` claim MUST name the {abbr-api}, and the {abbr-api} MUST reject a token without its own identifier there.
A client SHOULD ask for that audience with the `resource` parameter of link:https://www.rfc-editor.org/info/rfc8707[RFC 8707].
A token that many APIs accept lets any one of them replay it against the others.

[[IAM-031]]
*IAM-031.* An {abbr-api} MUST check a self-contained access token under link:https://www.rfc-editor.org/info/rfc9068[RFC 9068].
Its `typ` header MUST be `at+jwt`, and its signature MUST use an algorithm from a fixed list of asymmetric algorithms.
The {abbr-api} MUST reject the algorithm `none`, and MUST follow the other checks of link:https://www.rfc-editor.org/info/rfc8725[RFC 8725].
For an opaque token, the {abbr-api} MUST ask the authorization server under link:https://www.rfc-editor.org/info/rfc7662[RFC 7662].
A token that IAM-026 binds to a key MUST come with a valid proof of that key.
Most token flaws come from a server that trusts a header the attacker wrote.

[[IAM-032]]
*IAM-032.* An access token MUST expire within 15 minutes, and within 5 minutes at the `high` level.
The authorization server MUST bind each refresh token of a public client to a key, or rotate it.
link:https://www.rfc-editor.org/info/rfc9700[RFC 9700] requires the same.
A refresh token MUST NOT outlive the session that it belongs to, under IAM-040.
The authorization server MUST offer revocation under link:https://www.rfc-editor.org/info/rfc7009[RFC 7009].
A short life limits the harm of a leaked token, since an {abbr-api} cannot recall a self-contained one.

At the `high` level, the 5-minute limit follows the federal link:https://www.cyber.gc.ca/en/guidance/user-authentication-guidance-information-technology-systems-itsp30031-v3[guidance ITSP.30.031 v3] on user authentication.
Its section 7.3 makes an assertion sent to another domain expire within 5 minutes.
An access token at that level reaches other services in the same way, so it gets the same limit.

[[IAM-033]]
*IAM-033.* An {abbr-api} that accepts tokens MUST publish its metadata under link:https://www.rfc-editor.org/info/rfc9728[RFC 9728].
The metadata lives at `/.well-known/oauth-protected-resource`.
It names the authorization servers, the scopes and whether each token needs a key binding.
A client can then find, without guesswork, how to get a token for the {abbr-api}.

== Assurance and scopes

[[IAM-034]]
*IAM-034.* An {abbr-api} MUST check the `acr` and `auth_time` claims against the level of each operation.
When they fall short, it MUST answer `401` with the error `insufficient_user_authentication` of link:https://www.rfc-editor.org/info/rfc9470[RFC 9470].
The challenge MUST carry `acr_values` with the required level, and `max_age` when the sign-in is too old.
The client then sends the person to sign in again at that level, which is a step-up.
A token for a lower level can then never reach an operation that needs a higher level.

[[IAM-035]]
*IAM-035.* A scope MUST name a coarse permission on one {abbr-api}, such as read access to its records.
A scope MUST NOT replace the check of each object and each field under API-092.
A scope that {abbr-fpsot-first} defines MUST be in kebab-case English, like a code list value under NAM-060.
A claim that {abbr-fpsot} defines MUST be in lowerCamelCase, like a field name under NAM-010.
A claim or a parameter from an outside standard MUST keep its exact name, under NAM-007, such as `auth_time`.
Scopes say what a client may ask for, while the {term-authorization-engine} decides what a person may do.

[[IAM-036]]
*IAM-036.* An access token MUST carry only the claims that its {abbr-api} needs.
The `sub` claim MUST be an opaque identifier, unique to the person within the issuer.
It MUST NOT be a social insurance number, a health insurance number, an email address or a name.
An identity provider SHOULD issue a pairwise `sub` to services of different organizations.
Tokens travel through logs, proxies and other systems, so every claim that a token holds spreads further.
