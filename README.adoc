= FPSOT identity and access specification

Rules for how public-sector software signs people in, issues and checks tokens, and decides who may do what.
It sets three assurance levels with their own `acr` values and a published mapping to Québec, Canada, the Pan-Canadian Trust Framework, eIDAS and NIST SP 800-63-4.
It profiles OpenID Connect and OAuth 2.0 on the floor of RFC 9700, with a backend for each browser front end and FAPI 2.0 at the high level.
Authorization goes through one engine over OpenID AuthZEN 1.0, with policies in plain Rego and exportable relationships.
It also covers passkeys and sessions, representation of another person or a business, workload identity, provisioning, audit events and problem types.
The rules name standards and capabilities, not products. Version 0.1 is a draft.

== Implement this spec

Read the normative text in `spec/en/` or `spec/fr/`.
Each requirement has an ID from `IAM-001` to `IAM-103`.

* Declare the level of each service and map it with `registry/assurance-levels.yaml` (IAM-001 to IAM-004).
* Sign people in with the authorization code flow and PKCE, through a backend for the front end (IAM-020 to IAM-028).
* Check audience, lifetime, level and key binding of each token at each API (IAM-030 to IAM-036).
* Call the authorization engine over AuthZEN on every request, and deny by default (IAM-050 to IAM-057).
* Model representation as relationships in the engine (IAM-060 to IAM-065).
* Emit the events of the catalog, and return the problem types of `registry/problem-types.json` (IAM-090 to IAM-103).

The page `spec/en/reference-stack.adoc` is informative and names the products of the FPSOT reference implementation.

== Adopt this spec

Read the guide in `docs/modules/en/pages/index.adoc` or `docs/modules/fr/pages/index.adoc`.
It walks one new service through the level, the sign-in, the API, the authorization engine and the events.
A request for proposals can require that a supplier meet this specification, or name a level of IAM-001.
The comparison data in `jurisdictions/` shows how the rules of Canada and Québec differ.
The page `spec/en/questions-for-counsel.adoc` lists the legal questions that remain open. The specification is not legal advice.

== Layout

[cols="1,3"]
|===
| Folder | Content

| `spec/`
| Normative text, in English and French. `book.adoc` joins the pages into one book.

| `registry/`
| `assurance-levels.yaml`, the level mapping, and `problem-types.json`, the problem types with English and French titles.

| `scripts/`
| The check of `problem-types.json` against the text, and its tests. CI runs them in the job `registry`.

| `docs/`
| Guides, in the Antora folder layout.

| `skill/`
| The agent skill: a short summary that cites requirement IDs.

| `rules/`
| Machine-checkable rules.

| `diagrams/`
| PlantUML sources and their rendered SVG files.

| `jurisdictions/`
| Comparison data: how each government handles the same topics.
|===
